# Plan project profile

Read by the `engineering` plugin's plan commands. Keep it accurate — it is the grounding for every
plan created in this repo. Update it when the repo changes shape (`/plan-init refresh`).

## What this repo is

Tooling that turns two Ramba S.S. albums into click-locked live backing tracks: drums rebuilt as
quantised MIDI, lyric/image video, and automatic BOSS GX-100 patch changes. The DAW is Reaper.

The thing a newcomer gets wrong: **`songs/` is not test data, it is the deliverable.** Each
`song.yaml` holds hand-measured musical facts (tempo to 0.01 BPM, section boundaries, `bars` counted
by ear from where the band stops) that cost real listening time to obtain. A plan that "regenerates"
them destroys work no code can recover. The second thing they get wrong: positions are in **bars**,
never seconds.

## Code placement rules

- **Default target for new logic: the core tier** in `src/rambass/`, as a pure function taking and
  returning `list[Hit]` / a performance object plus a report dict. That is what makes it testable
  without librosa, which is what makes it testable at all.
- **Dependency direction is one-way by weight.** core → nothing heavy; `analyze`/`transcribe` may
  import core; `stems` may import core. Never the reverse, and never a top-level
  `import librosa|scipy|demucs` outside those three files — use `audio.require_module()` so a missing
  extra produces an install hint instead of an ImportError traceback.
- `quantize.py` functions are **pure**: performance in, performance out. They must not touch disk.
- Anything random takes a **seed**. Re-running after one setting changes must not reshuffle the song.
- Drum data travels as **instrument names** (`kick`, `hihat_open`), never note numbers. Note numbers
  appear only at MIDI write time, via a `DrumMap`.
- **Read-only / do-not-hand-edit paths**: `reaper/build/*.rbs` (generated), `songs/**/video/*.ass`
  (generated), `songs/**/midi/drums-*.mid` (regenerated by the pipeline — hand edits belong in
  `song.yaml` as `drums.additions`/`drums.removals`), and any `render/` output.
- Practice-track code may **not** write to `render/`, may not edit a musical field in `song.yaml`,
  and its stages are **not** added to `manifest.STAGES`.

## Architectural principles

1. **Store positions in bars, never seconds.** Convert once, in `timeline.py`, from the tempo in
   `song.yaml`. A seconds value in a manifest breaks the ability to change a song's tempo, and that
   will not surface until someone changes one.
2. **Honour the three documented exceptions and add no fourth without saying why**: `lyrics.srt`
   (hand-timed against a fixed master), `practice/align.yaml` (describes an immutable audio file, and
   stores only the source side), and Reaper **marker labels** (ruler numbers, `bar + count_in.bars`).
3. **Keep the two clocks distinct.** `bar_beat_to_seconds()` is musical zero (count-in is negative);
   `audio_time()` is the first rendered sample (what Reaper, ffmpeg and subtitles get). Mixing them
   shifts everything by the count-in length.
4. **Bar numbers spoken aloud are Reaper ruler readings; bar numbers in `song.yaml` are musical.**
   Subtract `count_in.bars` before writing anything down, and echo both numbers back when confirming.
5. **Never derive `bars` from audio duration.** These recordings are longer than the song; the
   difference is exactly the material to discard.
6. **A tuning constant is per-album, not per-song.** One drummer, one kit, one studio across Tutti in
   Fila — so a new threshold must be checked against a second song of that album before it becomes a
   default, and a per-song override is a smell. Nothing calibrated on Tutti in Fila may be reasoned
   with about Diversamente Giovani (electronic drums).
7. **Never rebuild a derived file implicitly.** `provenance.py` / `rambass stale` report staleness and
   its three causes (input changed, `song.yaml` changed, producing code changed). A re-transcription
   is minutes of CPU and can change the part under you.
8. **Read `CLAUDE.md`'s "Facts that were verified" before proposing anything in the drum, warp or
   cymbal-detection area.** Roughly a dozen questions there are closed by measurement — fixed tempo
   vs tempo map, WSOLA vs resampling, crash-vs-open-hat, Manlio's verse-2 sidestick. A plan that
   reopens one is invalid unless it names new evidence.

## Build & verification

- **Build**: no build step (editable install: `uv pip install -e '.[audio]'`). Use `uv pip`, not
  `pip`: `.venv` here is a `uv venv` and has no pip in it. `make` is not installed on this machine
  either, so run the underlying commands rather than the `Makefile` targets.
- **Unit tests**: `pytest -q` — 779 tests, ~32s, all green at HEAD
- **Scoped tests**: `pytest -q tests/test_<area>.py -k <expr>` — pick the file from the module you
  touched (`test_align.py`, `test_drum_passes.py`, `test_sidestick.py`, `test_timeline.py`, …)
- **Manifest validation**: `rambass check` — validates every `song.yaml`; instant
- **Lint / format**: `ruff check src tests` / `ruff format src tests`
- **Warnings as errors**: no. Note: `ruff check` reports **21 pre-existing errors** at HEAD
  (10 I001, 5 F541, 3 F401, 3 B905, mostly `cli.py`). New code should be clean; do not treat the
  existing count as a regression you caused, and do not bulk-fix it inside an unrelated plan.
- **Do NOT run unprompted**: `rambass stems separate` (demucs, minutes of CPU),
  `rambass drums transcribe` (re-transcription can change the part under you), `rambass align --warp`
  and any `video` / `click` render (ffmpeg, large files). Nothing here touches a live system, but all
  of it is slow and some of it overwrites hand-tuned output.
- **ffmpeg**: installed on this machine but unlinked by winget. Check `RAMBASS_FFMPEG` before telling
  anyone to install it — point it at `%LOCALAPPDATA%\Microsoft\WinGet\Packages\Gyan.FFmpeg_*\bin`.
- **Quality gate (Stop hook)**: `.venv\Scripts\pytest.exe -q && .venv\Scripts\rambass.exe check`

  The venv paths are deliberate and load-bearing. The Stop hook runs this through `cmd.exe` with no
  virtualenv activated, so bare `pytest` / `rambass` do not resolve there even though they resolve
  in an interactive shell — the gate failed with "'pytest' is not recognized" until the paths went
  in. On POSIX the equivalent is `.venv/bin/pytest -q && .venv/bin/rambass check`. Verified under
  `cmd.exe /d /s /c`: 700 passed, manifests consistent, exit 0.

## Success-criteria conventions

- **Automated gate**: `pytest -q` green, `rambass check` clean, and `ruff check src tests` reporting
  no *new* findings.
- **Test-first is mandatory here, including for changes that look too small to need one.** The
  algorithms are tuned by ear against one song; a threshold that fixes Manlio silently breaks Tutti
  in Fila unless a test pins it.
- **A number that came from a measurement gets a test naming the measurement.** A constant with a
  story and no test is a constant somebody will "clean up".
- **Verification done by hand belongs in `tests/`, not in the transcript.** If a phase checks a fix
  with a one-off script or a hash comparison, that check *is* the deliverable test.
- **Manual/musical check**: anything affecting audible output (velocities, articulation, warp, click)
  needs a listen by Paolo named as an explicit phase step — a passing test does not establish that a
  rim click is audible under the hi-hats.
- **Progress board**: `rambass status` (or `--markdown`) is the project-level measurement instrument.
- A plan touching drum detection should say which **second song of the album** it was checked against.

## Version management

This repo does not version-bump per change. `pyproject.toml` sits at `0.1.0`, there are no tags and
no CHANGELOG. Do not add a bump step to a plan.

## Repo etiquette

- **Default branch**: `main`
- **Branch naming**: none — **work directly on `main`** and push. Paolo is the only maintainer; do
  not create a branch or a PR unless explicitly asked. (The stale `remotes/origin/claude/*` branches
  are dead history, not a convention.)
- **Issue tracker**: `github` — `paolodona/rambass-live`, `gh` authenticated. The `/issue-start`,
  `/issue-pr` and `/backlog-sync` commands are available, but the repo has no
  `.github/ISSUE_TEMPLATE/` and no workflows, and the branch-per-issue flow those commands assume
  conflicts with "work directly on `main`".
- **Commit convention**: not conventional commits. Subjects are descriptive sentences in the
  indicative, saying what changed and often why — e.g. *"The declared side-stick is audible now, and
  the level lives in song.yaml"*, *"The first detected beat is not bar 1, and three false alarms in
  the report"*. Occasional `Docs:` prefix. No ticket reference required.
- **AI attribution in commits**: required — `Co-Authored-By: Claude Opus 5 (1M context)
  <noreply@anthropic.com>` on every recent commit.
- **Never commit audio, video or images.** `.gitignore` covers them; check before `git add -A` — it
  has swept debug MIDI back in twice.
